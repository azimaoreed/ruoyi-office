# 本地开发与部署说明

本文基于当前仓库 `/Users/azimao/work/demo/ruoyi-office` 的实际结构整理，重点回答以下 4 个问题：

1. 本地使用 IDEA 开发，如何配置环境
2. 项目如何在本地完成编译和构建
3. 项目如何通过本地 Docker 和远程 Docker 运行
4. 构建出的容器是否支持单独部署

---

## 1. 项目结构与推荐运行方式

当前项目是一个 Maven 多模块工程，根模块在 `pom.xml` 中声明了 `yudao-server`、`yudao-gateway` 以及多个业务模块。

- 单体容器入口：`yudao-server`
- 微服务入口：`yudao-gateway` + `yudao-module-xxx-server`
- 推荐本地开发方式：`yudao-server` 单体模式

原因：

- `yudao-server` 本身就是一个“容器应用”，通过引入哪些 `yudao-module-xxx-server` 依赖决定最终启用哪些模块
- 单体模式默认关闭了 Nacos 注册中心和配置中心
- 单体模式本地只需要 MySQL + Redis，依赖最少

对应文件：

- `pom.xml`
- `yudao-server/pom.xml`
- `yudao-server/src/main/resources/application.yaml`
- `docs/按需部署指南.md`

## 2. 本地 IDEA 开发环境配置

## 2.1 必备软件

建议安装以下软件：

- JDK 17
- IntelliJ IDEA
- Maven 3.8+
- Docker Desktop
- MySQL 8.x
- Redis 7.x

说明：

- 根 POM 明确指定 `java.version=17`
- 当前仓库已实测可以用 Maven 本地打包成功
- Docker 和 Docker Compose 也已具备

## 2.2 IDEA 导入步骤

1. 使用 IDEA 打开仓库根目录：

```text
/Users/azimao/work/demo/ruoyi-office
```

2. 选择以 Maven 项目导入。

3. 安装 IDEA 的 `Lombok` 插件。

4. 在 IDEA 中开启注解处理：

- `Settings -> Build, Execution, Deployment -> Compiler -> Annotation Processors`
- 勾选 `Enable annotation processing`

5. 设置 Project SDK：

- `Project SDK = JDK 17`
- `Project language level = 17`

6. 设置 Maven Runner JDK：

- `Settings -> Build Tools -> Maven -> Runner -> JRE`
- 选择本机 JDK 17

7. 建议关闭 IDEA 自己的 Build，优先使用 Maven 构建。

## 2.3 为什么一定建议使用 JDK 17

当前机器虽然可以用更高版本 JDK 编译，但项目的目标版本是 17。

如果直接用 21/25，虽然这次构建没有失败，但会看到编译告警，长期不建议作为团队统一开发基线。最稳妥的方案仍然是：

- 本地安装并固定 JDK 17
- IDEA 和 Maven 都指向 JDK 17

默认本地 profile 是 `local`，配置如下：

- 服务端口：`48080`
- MySQL：`127.0.0.1:33061`
- 数据库名：`ruoyi-office`
- 用户名：`root`
- 密码：`123456`

对应文件：

- `yudao-server/src/main/resources/application.yaml`

创建数据库：

```sql

```

导入以下 SQL：

- `sql/mysql/ruoyi-vue-pro.sql`

注意：

- SQL 文件名虽然叫 `ruoyi-vue-pro.sql`，但当前本地配置连接的数据库名称已经是 `ruoyi-office`

## 2.6 本地运行方式

在 IDEA 中新增 Spring Boot 启动项：

```bash

```

启动后可访问：

- 健康检查：`http://localhost:48080/actuator/health`
- Swagger：`http://localhost:48080/swagger-ui`

## 3. 本地编译与构建

## 3.1 推荐构建命令

在仓库根目录执行：

```bash
mvn -Pboot -pl yudao-server -am clean package -DskipTests
```

说明：

- `-Pboot`：单体模式构建
- `-pl yudao-server`：只从 `yudao-server` 这个入口开始构建
- `-am`：自动补齐它依赖的模块

## 3.2 构建产物

构建成功后，产物位于：

```text
yudao-server/target/yudao-server.jar
```

## 3.3 已验证结果

当前仓库已经实际验证通过以下命令：

```bash
mvn -Pboot -pl yudao-server -am clean package -DskipTests
```

结果为：

- `BUILD SUCCESS`
- 产物成功生成 `yudao-server/target/yudao-server.jar`

## 3.4 为什么会编译出很多模块

虽然入口是 `yudao-server`，但它会自动带上它依赖的模块一起编译。

当前 `yudao-server/pom.xml` 中启用了：

- `yudao-module-system-server`
- `yudao-module-infra-server`
- `yudao-module-bpm-server`

因此构建时会把这些模块及其底层依赖链一并编译，这是正常行为。

## 3.5 如何控制“只构建需要的功能”

单体模式下，不是改启动命令，而是改：

```text
yudao-server/pom.xml
```

保留需要的依赖，注释不需要的依赖。例如：

- 最小后台：保留 `system + infra`
- OA/HR：保留 `system + infra + bpm + oa + hrm`
- BPM 最小化：保留 `system + infra + bpm`

## 4. 本地 Docker 运行

本地 Docker 推荐两种方式。

## 4.1 方式一：Docker 只跑中间件，IDEA 跑后端

这是最推荐的开发方式。

优点：

- 断点调试最方便
- 改代码后不需要反复重建镜像
- 数据库和 Redis 又能保持容器化一致性

建议：

- MySQL 用 Docker 映射到本地 `33061`
- Redis 用 Docker 映射到本地 `6379`
- 后端直接在 IDEA 用 `local` profile 启动

示例：

```bash
docker run -d \
  --name ruoyi-office-mysql \
  -p 33061:3306 \
  -e MYSQL_ROOT_PASSWORD=123456 \
  -e MYSQL_DATABASE=ruoyi-office \
  mysql:8.0.33 \
  --default-authentication-plugin=mysql_native_password \
  --character-set-server=utf8mb4 \
  --collation-server=utf8mb4_general_ci \
  --lower_case_table_names=1
```

```bash
docker run -d \
  --name ruoyi-office-redis \
  -p 6379:6379 \
  redis:7.2
```

之后导入 SQL，再在 IDEA 启动后端即可。

## 4.2 方式二：后端也打成 Docker 镜像运行

先构建 Jar：

```bash
mvn -Pboot -pl yudao-server -am clean package -DskipTests
```

再构建镜像：

```bash
docker build -t yudao-server:latest ./yudao-server
```

Dockerfile 已经准备好：

- 基础镜像：`eclipse-temurin:21-jre`
- 默认暴露端口：`48080`
- 默认启动命令：`java ${JAVA_OPTS} -jar app.jar $ARGS`

## 4.3 使用仓库自带 compose

仓库包含：

```text
yudao-server/docker-compose.yml
```

这个文件当前状态是：

- `mysql` 服务被注释
- `redis` 服务被注释
- `yudao-server` 服务已保留

因此它更像“部署模板”，不是开箱即用的本地一键启动文件。

如果要本地直接使用，有两种做法：

1. 取消注释 `mysql` 和 `redis` 服务
2. 保持它们注释，只让 `yudao-server` 连接外部现有 MySQL/Redis

## 4.4 本地容器运行示例

如果你本地已有 MySQL 和 Redis，可以直接这样运行后端容器：

```bash
docker run -d \
  --name yudao-server \
  -p 48080:48080 \
  -e SPRING_PROFILES_ACTIVE=prod \
  -e MYSQL_URL='jdbc:mysql://host.docker.internal:33061/ruoyi-office?useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true&nullCatalogMeansCurrent=true&rewriteBatchedStatements=true' \
  -e MYSQL_USERNAME=root \
  -e MYSQL_PASSWORD=123456 \
  -e REDIS_HOST=host.docker.internal \
  -e REDIS_PORT=6379 \
  -e REDIS_DATABASE=0 \
  yudao-server:latest
```

说明：

- macOS Docker Desktop 下容器访问宿主机可使用 `host.docker.internal`
- 这里使用 `prod`，是因为 `application-prod.yaml` 已支持环境变量注入

## 5. 远程 Docker 运行

远程 Docker 分两类：单体容器部署、微服务容器部署。

## 5.1 远程单体容器部署

这是当前仓库最适合落地的方式。

步骤：

1. 本地或 Jenkins 构建 Jar
2. 将 `yudao-server.jar`、`Dockerfile`、`docker-compose.yml` 上传到远程服务器
3. 在远程服务器构建镜像
4. 使用 `docker compose up -d` 启动

远程目录建议：

```text
/data/app/yudao-server
```

远程命令示例：

```bash
cd /data/app/yudao-server
mkdir -p target
mv yudao-server.jar target/
docker build -t yudao-server:latest .
docker compose up -d
```

## 5.2 远程环境变量覆盖

`application-prod.yaml` 已支持如下环境变量：

- `MYSQL_URL`
- `MYSQL_USERNAME`
- `MYSQL_PASSWORD`
- `MYSQL_SLAVE_URL`
- `MYSQL_SLAVE_USERNAME`
- `MYSQL_SLAVE_PASSWORD`
- `REDIS_HOST`
- `REDIS_PORT`
- `REDIS_DATABASE`
- `REDIS_PASSWORD`
- `PLUGINS_DIR`

因此远程部署时不需要改 Jar 包，只要改环境变量即可。

## 5.3 Jenkins 自动化部署

仓库已经提供：

```text
yudao-server/Jenkinsfile
```

当前流水线做了这些事：

1. 拉取代码
2. Maven 构建 `yudao-server`
3. 传输 Jar 和 Dockerfile 到远程服务器
4. 在远程服务器执行 `docker build`
5. 部署或重启容器

如果你们团队使用 Jenkins，这个文件可以直接作为基线继续维护。

## 6. 微服务运行方式

## 6.1 什么时候才建议用微服务

只有在下面场景才建议用：

- 需要 `Gateway`
- 需要 Nacos 注册中心/配置中心
- 需要服务拆分与独立扩缩容
- 需要只运行部分服务并对外暴露统一网关

如果只是本地开发或常规单项目部署，不建议一开始就上微服务。

## 6.2 微服务最小集合

至少需要：

- `yudao-gateway`
- `yudao-module-system-server`
- `yudao-module-infra-server`
- 可选业务服务，例如 `yudao-module-bpm-server`
- Nacos
- MySQL
- Redis

## 6.3 微服务端口

当前项目中已定义：

- `gateway-server`：`48080`
- `system-server`：`48081`
- `infra-server`：`48082`
- `bpm-server`：`48083`

## 6.4 微服务构建示例

只构建网关、系统、基础设施、BPM：

```bash
mvn -Pcloud -pl \
  yudao-gateway,\
  yudao-module-system/yudao-module-system-server,\
  yudao-module-infra/yudao-module-infra-server,\
  yudao-module-bpm/yudao-module-bpm-server \
  -am clean package -DskipTests
```

## 6.5 微服务 Docker 编排

仓库中有参考模板：

```text
script/docker/docker-compose.yml
```

但需要注意，这个模板不是本地一键可跑状态，里面仍然需要你替换：

- `[YOUR_NACOS_ADDR]`
- `[YOUR_NAMESPACE]`
- `[YOUR_SKYWALKING_ADDR]`

同时，它采用 `network_mode: host`，更偏向服务器环境，不建议直接拿来当本地开发编排。

## 6.6 网关路由说明

网关路由都写在：

```text
yudao-gateway/src/main/resources/application.yaml
```

如果只启动部分服务，建议同步删除或注释不需要的 routes，避免：

- 网关访问 503
- Swagger 聚合里出现无效服务

## 7. 构建出来的容器是否支持单独部署

支持。

这是当前项目最重要的部署特性之一。

原因如下：

1. `yudao-server` 就是单体容器应用
2. 单体模式默认关闭 Nacos
3. 只要外部提供 MySQL 和 Redis，容器即可独立运行
4. 需要启用哪些业务模块，取决于 `yudao-server/pom.xml` 中引入了哪些 `yudao-module-xxx-server`

也就是说，当前项目完全支持以下部署模式：

- 一个 `yudao-server.jar`
- 一个 `yudao-server` Docker 镜像
- 外部一个 MySQL
- 外部一个 Redis

这就是“容器支持单独部署”的含义。

## 8. 按需部署建议

## 8.1 最小后台

保留：

- `yudao-module-system-server`
- `yudao-module-infra-server`

适合：

- 后台基础平台
- 用户、角色、权限、文件、任务等基础能力

## 8.2 BPM 最小化

保留：

- `yudao-module-system-server`
- `yudao-module-infra-server`
- `yudao-module-bpm-server`

适合：

- 只上线流程引擎能力

## 8.3 OA / HR 协同

保留：

- `system`
- `infra`
- `bpm`
- `oa`
- `hrm`

适合：

- 内部办公、人事协同

## 8.4 注意菜单数据

即使后端不引入某个模块，数据库里如果还保留对应菜单，前端点击时仍可能报：

- 404
- 500
- 网关 503

因此按需部署通常要同时做两件事：

1. `yudao-server/pom.xml` 控制后端模块
2. 数据库菜单做软删除或裁剪

## 9. 当前仓库需要特别注意的事项

## 9.1 当前仓库更适合“后端开发与部署”

`yudao-ui` 目录下目前只有各前端项目的 `README.md`，没有完整前端源码和 `package.json`。

这意味着：

- 当前仓库可以完整支撑后端本地开发、编译、打包、部署
- 但如果要联调前端，需要另外补齐前端项目源码

## 9.2 生产环境不要直接沿用示例密钥

配置文件中存在较多第三方平台示例配置、测试账号或默认密码。

上线时建议：

- 优先使用环境变量
- 把敏感信息移到外部配置中心或服务器环境变量
- 修改默认数据库和 Redis 密码

## 10. 推荐落地方案

如果目标是“尽快让团队本地能开发、服务器能稳定部署”，推荐按下面执行：

1. IDEA 本地开发统一使用 `JDK 17`
2. 本地运行统一采用：
   - Docker 启 MySQL + Redis
   - IDEA 跑 `yudao-server`
3. 构建统一使用：
   - `mvn -Pboot -pl yudao-server -am clean package -DskipTests`
4. 部署统一先走单体容器：
   - `yudao-server.jar`
   - `Dockerfile`
   - `docker compose`
5. 真正出现网关、服务拆分、独立扩容需求时，再切换到微服务架构

这样成本最低，路径最稳。
